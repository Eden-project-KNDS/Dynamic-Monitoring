## Performance Profile Analysis (Flame Graphs) of the `slurm-monitor` Daemon

Almost all CPU time is spent waiting for the hardware driver to respond, rather than executing Go logic. The differences between the individual graphs are cosmetic and stem primarily from the exact moment the profiler sampled various NVIDIA API queries (e.g., querying utilization vs. temperature).


*   **Metrics Collection (Prometheus and Go code):** At the lowest layers, you can see the main `slurm-monitor` process calling the Prometheus library (e.g., `prometheus.(*Registry).Gather.func1` and `prometheus.safeCollect`), which initiates the routine data collection. Above this, daemon's methods are executed, including `slurm-monitor/monitor.(*gpuMonitor).getGpuStats` and `(*Collector).collectGPUs`. The width of these blocks perfectly matches the blocks directly above them, proving that our custom Go code is merely delegating tasks and executing zero expensive loops.
*   **The Language Barrier (Cgo):** Above the daemon's code, you can observe the `runtime.cgocall` and `runtime.asmcgocall.abi0` layers. These represent the moment the Go runtime suspends the goroutine and crosses the bridge (Cgo) into the native C library.
*   **The Hardware Bottleneck (NVIDIA Driver and NVML):** The widest, most massive blocks dominating the graphs are functions executing inside the shared library `[libnvidia-ml.so.580.178.04]`. The kernel functions visible at the very top (e.g., `_nv049612rm`, `_nv046457rm`) and native `ioctl` system calls are used for hardware communication with the GPU during queries like `nvmlDeviceGetUtilizationRates`, `nvmlDeviceGetTemperature`, and `nvmlDeviceGetPowerUsage`.
*   **Background and Runtime Threads (Right side of the graphs):** The completely detached, narrow towers on the right side represent background processes maintaining the program's operation. These include the internal Go thread monitor (`runtime.sysmon`, `runtime.mstart`), routine thread sleeping (`do_nanosleep`, `runtime.usleep`), and episodic reads of the cgroup container limits by the Go runtime (`internal/runtime/cgroup.ReadCPULimit`). They have a negligible impact on overall resource consumption.

The most important takeaway from these graphs is the **complete absence of memory cleanup operations (Garbage Collection)**. Unlike the previous issues caused by `filepath.WalkDir`, there is no trace of calls like `runtime.mallocgc` on these current profiles.
